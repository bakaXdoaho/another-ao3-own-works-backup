# Design Notes — 备份自己的 AO3 作品时踩过的坑

Claude Opus 5

> 这份笔记是 `another-ao3-own-works-backup` 的设计依据。
> 代码注释里的 `N-xx` 都指向这里。
>
> **每一条都是实测得来的**，不是猜的，也不是从别处抄的。
> 凡是写「实测」的地方，都真的跑过并对过账；没验过的会明说。
>
> 这份笔记面向**想给自己的作品做备份的人**。
> 它不教你怎么抓别人的文 —— 这个工具也做不到那件事（见 README）。

## 一、最要紧的三条

这三条的共同点：**HTTP 状态码是 200，页面看起来正常，但内容是错的。**
只看 status code 的脚本会把它们当成功，静默污染整个存档 —— 而且当时不会有任何报错。

### N-01 限流页返回 HTTP 200

AO3 被压到限流时返回的「Retry later」页，**状态码是 200**，body 很短。

→ **必须按 body 特征判定，不能只看状态码。**
  这是头号杀手：一次没拦住，库里就多一篇内容是「Retry later」的「作品」，
  而它的文件大小、下载时间看起来都很正常。

### N-02 「Lost Cookie / Forced Logout」页也返回 200，而且带着登录标记

比 N-01 更阴险的一种。当 cookie 给得不全时，
下载接口会返回一个 Forced Logout 页 —— 它**同时满足**：

- HTTP 200
- 页首照样渲染着 `Hi, 你的用户名!`
- 带着 `id="greeting"`

也就是说，**「检查页面上有没有自己的用户名」这个常见做法会被它骗过去。**

→ 两条应对：
  1. **先查是不是 Forced Logout 页，再查登录标记**，顺序不能反
  2. cookie 要给**整条 Cookie 请求头**，不能只给 `_otwarchive_session`
     （下载接口会检查不止一个 cookie）

> 这一条是实测撞出来的：当时三个响应全被 fail-closed 的校验拦下，
> 存档一个字节都没被污染。**那道校验是这个项目里最值钱的十行代码。**

### N-03 fail closed：只接受「确实像目标页面」的响应

由 N-01 / N-02 直接推出的通用做法：

- 每种页面写一个 `looks_like_xxx()`，**先否决再接受**
- 校验不过的**不入库**，原样存到一个隔离目录里留给人看
- 宁可漏，不可错：漏了重跑一次就有，错了要很久以后才发现

判据可以很朴素：长度是否过短、页面里有没有出现本篇的 work id、
关键容器在不在。朴素但管用。

## 二、官方下载件的结构

### N-04 章节切分必须靠「直接子节点」

官方 HTML 下载件的骨架：

```
div#preface
└─ div.meta > dl.tags        ← 全部 tag + Language + Series + Stats
div#chapters
├─ div.meta.group            ← h2 章标题 + Chapter Summary + Chapter Notes
├─ div.userstuff             ← 正文
├─ div.meta.group            ← 下一章…
├─ div.userstuff
└─ div.meta                  ← Chapter End Notes（注意：不带 group）
div#afterword
```

**⚠️ 陷阱**：`class="userstuff"` **不只用于正文**。
Chapter Summary 与 Chapter Notes 的 blockquote 也带这个类。
实测在一篇 5 章的作品里，`userstuff` 出现 **19 次**，其中只有 5 次是正文。

→ **必须扫 `div#chapters` 的直接子节点并记住顺序**，不能全文搜关键词：
  - 顶层 `div.meta.group` = 这一章的头
  - 顶层 `div.userstuff` = 这一章的正文
  - 顶层 `div.meta`（**不带 group**）= 上一章的章末注

### N-05 `<dt>` 标签会按数量变单复数

preface 里的字段名不是固定的：

| 字段 | 单数形 | 复数形 |
|---|---|---|
| Fandom | `Fandom:` | `Fandoms:` |
| Relationship | `Relationship:` | `Relationships:` |
| Archive Warning | `Archive Warning:` | `Archive Warnings:` |
| Category | `Category:` | `Categories:` |
| 恒为复数 | — | `Characters:` `Additional Tags:` `Collections:` |
| 恒为单数 | `Rating:` `Language:` `Series:` `Stats:` | — |

→ **用前缀匹配（去掉冒号后 `startswith`），不要精确匹配全名。**
  精确匹配会在「只有一个 fandom」的作品上静默丢字段。

### N-06 Relationship 里的 `/` 与 `&` 语义不同

`/` = 恋爱向，`&` = 友情 / gen 向。AO3 的 Category 字段也会相应是 `Gen`。

→ 若按 CP 做统计，**必须保留这个区分**，不能统一当成「CP」——
  否则「写了他俩的友情」会被算成「写了他俩的恋爱」。

### N-07 Collections 非空时才出现

`Collections:` 整块在没有合集时**完全不出现**，不是出现一个空值。

→ 解析要容许整块缺席；**不必为此每篇多发一次请求去确认。**

### N-08 章节数可能是 `n/?`

未完结作品是 `5/?` 而不是 `5/5`。解析要容错，
且「是否完结」可以直接从这里派生，不必另存字段。

## 三、字数与日期

### N-09 中文字数口径与容差对账

计数方法（这是一种可行口径，不是唯一正确答案）：
**只数汉字 + 拉丁词元 + 假名；标点、空白、summary / notes 均不计入。**

实测：一篇 5 章作品按此口径算得 39,141，AO3 标 39,135 —— **误差 6 字（0.015%）**。

→ 两条建议：
  1. **用「本地分章合计 vs AO3 官方总数」做每篇的自动对账**，差个位数即视为通过
  2. **口径要带版本号**。改了计数规则就换版本号，否则历史数字无从对照

> 顺带：AO3 自己不同页面之间也会差几个字。别追求完全相等，
> 要紧的是这个差**可解释、可复现**。

### N-10 分章日期来自 `/navigate`，但它是「发布日期」

`https://archiveofourown.org/works/{id}/navigate`
格式极规整：`N. 章标题 (YYYY-MM-DD)`，一条正则即可。

**三个必须知道的限定**：

1. 这是**发布**日期，不是最后**修改**日期。AO3 任何地方都不提供后者
   → 字段就该叫 `published_at`，别叫 `date`
2. 作者**可以手动把它改成任意过去日期**（常见做法：改成预定发布日）
3. 因此 **日期不保证单调递增**，排序一律按章节序号

### N-11 ⚠️ 作为作者登录时，`/navigate` 会连草稿章一起列出来

这是一个**只有作者本人才会遇到**的差异：登录状态下，
`/navigate` 列出的章节数可能多于公开可见的章节数，多出来的是**未发布的草稿**。

→ 两条：
  - 已公开的章数以索引页 `13/23` 里的 **13** 为准，其后的标 `is_draft`
  - **往任何公开的地方导出时必须过滤掉草稿章** —— 这是最容易出事的一处

## 四、标签

### N-12 AO3 的标签计数是 canonical，blurb 里的是字面

在作品页侧边栏看到的某个 CP 计数，可能**大于**你按 blurb 标签统计出来的数。
**两个数都对，只是口径不同。**

机制：AO3 的 tag wrangler 会把 `implied X` 这类标签设为 `X` 的同义 / 子标签。
筛选侧边栏按 **canonical 标签**计数（已归并），
blurb 里显示的是**作者当初写下的字面标签**。

实测验证方式：`字面数 + implied 变体数 = 侧边栏数`，逐项对得上。

→ 三条规则：
  1. **字面标签永不改动**，`implied X` 原样存
  2. **默认统计口径走 canonical**（跟随 AO3）
  3. **归并关系单独存一张表**，随时可关掉这一层回到纯字面口径

> 一般化的说法：**事实与解释分开存，解释可重算。**
> 只用字面标签做「某 CP 累计多少字」会**系统性少算**，而且不会报错。

### N-13 索引页 HTML 里就带着筛选侧边栏

好消息：canonical 的 tag_id 与计数**不必额外请求** ——
索引页的筛选侧边栏里就有，抓索引时顺手解析即可。

## 五、评论

### N-14 评论层级藏在嵌套的 `<ol class="thread">` 里，不在 `<li>` 里

**这是写这套代码时踩得最深、也最有教育意义的一个坑。**

AO3 的评论区结构：

```html
<ol class="thread">
  <li class="… comment …" id="comment_1000001">
    <h4 class="heading byline">…作者、章节、时间…</h4>
    <blockquote class="userstuff">…正文…</blockquote>
  </li>
  <li>                        ← ⚠️ 没有 id 的空壳 li
    <ol class="thread">       ← 回复挂在**这里**
      <li … id="comment_1000002">   ← 才是上一条的回复
```

**回复并不嵌在被回复的那条 `<li>` 里面。**
被回复的 `<li>` 先闭合，然后跟一个**没有 id 的空壳 `<li>`**，
回复的 `<ol class="thread">` 才在那里面。

→ **层级只能由嵌套的 `<ol class="thread">` 数出来，与 `<li>` 无关。**

一种很自然、也很容易写出来的错法是数「栈上有几个评论 `<li>`」——
由于上面那个空壳结构，这个数**永远是 0**。
于是跑出「所有评论都是顶层、没有嵌套回复」—— 它不报错、不缺字段、
数量还和索引页对得上，**唯一不对的是它与事实相反**。

三条教训：

1. **「结果看起来合理」不等于「结果正确」。**
2. **该用解析器的地方别用括号计数。** 用标准库的 `html.parser`，别用正则数标签。
3. **要有能证伪自己的不变式**（见 N-16）。

### N-15 thread ≠ comment：两套口径

- AO3 的 stats 页报的是「Comment **Threads**」（评论**串**数）
- 索引页 blurb 里的 `comments` 是**评论条数**

一串 = 主评论 + 全部回复，**作者自己的回复也算在条数里**。
两个数都对，口径不同（与 N-12 是同一类问题）。

→ 建表时**必须把 thread 与 comment 分开**：
  主评论、回复、层级关系各自存好，否则「收到过多少评论」会答错。

### N-16 用不变式自查，而且要能证伪自己

评论解析写完后，加几条自动检查：

- **回复的时间必然晚于被回复的那条** —— 父子时间反了说明层级认错了
- 每条评论的 `parent_id` 必须在本页存在
- 层级为 0 的不该有父；层级 >0 的必须有父

**真正戳破 N-14 那个 bug 的是一句算术**：某篇只有 6 条是别人发的，
却报出 11 个「串」—— **串数不可能多于别人开的话头。**

→ 发现问题时**只报不改**：数据照实存下，判断交给人。

### N-17 拿评论的 URL 形式

实测三种：

| 形式 | 结果 |
|---|---|
| `/works/{id}?show_comments=true&view_full_work=true` | ✅ 能拿到全部评论，且跨章聚合 |
| `/works/{id}/comments` | ❌ 标题对，但一条评论都没有 |
| `/works/{id}/chapters/{cid}?show_comments=true` | 只出该章的 |

→ 用第一种，一篇一次请求最省。

**注意它会把全文正文也一并返回**（`view_full_work`）。
若正文已经存过，**只存评论区那一段**即可，别把作品再抄一遍。

实测：一篇 100+ 条评论、散在 20 多章上的长文，**单页全部返回，没有分页**。
但这不能证明任何规模都不分页 —— 代码里仍应检测分页，
并且**顺着页面自己给的 `href` 翻，不要自己拼参数**（拼错会静默抓空或抓错篇）。

## 六、图片

### N-18 append-only 资产池

图片一旦发布就基本不变；**会变的是「正文引用了哪些图」**。

模型：

- 资产以 URL 的 sha256 为键，**下载一次就永久保留**
- 重下作品时 diff `<img src>` 集合：新增的抓下来；
  **从正文里被移除的图，本地照样保留**，只标记 `referenced: false`
- 抓不到的（404 / 需登录）**记录状态**，日后可重试，**不要当成功处理**

> 理由：你把某张图从文里撤掉，不代表你想让备份也失去它。
> 这与「已删作品保留」是同一个原则。

### N-19 外部图床与 AO3 是两个独立的限流域

正文里内嵌的图片常常在第三方图床上。**别用同一个节流器** ——
图床是静态 CDN，比 AO3 轻得多，间隔可以短很多。

外部图床是这类存档里**时效性最强的一环**：AO3 上的文可以放很多年，
但图床链接说没就没。

## 六半、索引页：免费的数据源

### N-26 作品列表页的 blurb 里已经有很多东西

抓自己的作品列表时，每篇的 blurb 里就带着：标题、更新日期、rating、warnings、
category、fandom / relationship / character / freeform 全部标签、
series 归属与 part 号、字数、章节数（`n/m`）、以及 kudos / hits / comments / bookmarks 计数。

→ **这些都不必再为每篇单独发一次请求。**
  先把索引页抓全、解析透，能省下大量请求。

顺带两条实测：

- 下载 URL 里的 `{slug}` 部分与 `?updated_at=` 参数**都被忽略** ——
  URL 可以直接构造，不必先去作品页取。**但这一条请自己实测确认一遍再依赖它。**
- blurb 里的 summary **没有截断**（实测最长的几百字符都完整）

### N-27 变化触发式观测：数值只在变化时追加一行

kudos / hits / comments 这类计数会随时间变。想留时间序列，
**不要每次跑都存一份全量快照** —— 那会产生大量高度重复的记录。

模型：`observations(work_id, metric, value, observed_at)`，**只在数值变化时追加一行**。

- 零额外请求：数值本来就在索引页 blurb 里
- 零冗余：不变就什么都不写
- 对一个数值很少变动的库，这张表会长期保持很小

同样的思路适用于评论：以 comment_id 为键累积存储，
新的追加、改过的存新版本、**消失的标记为 gone 但内容永久保留** ——
别人删掉的评论，只有你的备份还有。

### N-28 按标签统计时，一篇多标签会被重复计入

「某个 CP 写了多少字」这类统计，一篇挂了多个 CP 的作品会被每个 CP 都算一次，
**所以各行相加会大于全库总字数**。

**这是对的**，不是 bug —— 问「这对 CP 写了多少」时，多 CP 的篇目本来就该算进去。
但**报表上必须写明**，否则看的人会以为算错了。

## 七、节流与会话

### N-20 间隔要从「上一次响应结束」开始算

实测：按 8 秒设置、而请求本身耗 1–3 秒，**真实间隔只有 5–7 秒**，
抓到第十几页就撞限流。

→ **从响应结束计时，不是从请求开始计时。** 并且把间隔放宽一些。

其它几条实测：

- **AO3 限流是跨连接共享的** —— 跑脚本时自己别同时刷 AO3
- **登录态下限流按账号计**，比游客更容易撞
- 遇到限流是正常现象，**不是被封**。等几分钟再续即可

### N-21 真正打断长任务的多半不是限流

实测：一次三小时的抓取被打断 8 次，**没有一次是 429**，
全是服务端 / CDN 侧的临时故障（5xx、读取超时）。

→ 重试逻辑要**同时**覆盖两类，且等待时间不同：
  限流等几分钟，临时故障等一分钟就够。
  把重试放在**客户端底层**，所有脚本自动获得韧性，别在每个脚本外层各写一遍。

### N-22 运行期会话守卫

session cookie 会过期。长任务中途掉登录会**静默拿到游客视图**
（受限作品直接 404），而不是报错。

→ 每次拿到页面都顺手校验一次登录状态，掉了就**停**，不要继续跑。
  另外：**登录失效不要自动重试** —— 等多久都没用，必须人去重取 cookie。

## 八、存储原则

### N-23 原始文件才是存档，数据库只是派生物

- 先落原始字节，再解析
- **绝不原地覆盖**
- 解析器改了、字段加了、发现 bug 了，**从本地原始件重建即可，不必重新联网**

一句可操作的判据：

> **删掉之后能不能从别的东西重新造出来？**
> 能 → 派生物，不必进版本库。不能 → 存档，只增不删。

### N-24 「清空重建」在重建源比目标窄时，等于隐性删除

一个实测踩到的真漏洞：重建脚本会 `DROP` 索引表再从**当前**列表页重建。
如果某篇作品已从站上删除，它就不在当前列表页里 ——
于是重建后**那一行凭空消失**，虽然本地文件还好好地躺着。

**文件在、库里却查不到，等于把已删作品弄丢了。**

→ 修法：重建后，把「本地有文件、但当前列表里没有」的记录**原样补回去**并标记消失时间。

→ 一般化的教训：**任何「清空重建」都要先问一句 ——
  重建的源，是不是比要重建的目标更窄？** 是的话，那就是一次隐性删除。

### N-25 只发 GET，并且用白名单挡住其它一切

- 代码里**根本没有** POST / PUT / DELETE
- URL 白名单集中在一处，不在名单里的一律拒绝
- 第二道保险：路径里含 `edit` / `delete` / `new` 等字样的直接拒绝

> 这不是防别人，是防自己写错。备份工具在别人的站上，
> **能力越小越好** —— 做不到的事就永远不会做错。

## 九、这份笔记本身的教训

回头看，上面这些坑分成两类，而**第二类比第一类难对付得多**：

| | 表现 | 例子 |
|---|---|---|
| 第一类 | **报错**，你立刻知道 | 404、连接超时、解析抛异常 |
| 第二类 | **不报错，结果看着正常** | N-01 限流页、N-02 假登录页、N-14 层级全 0、N-12 少算标签 |

第二类的共同应对只有一条：

> **别信提示，去看实际状态；并且给自己准备一个能证伪的对照量。**

这个项目里管用的对照量都很朴素 ——
本地分章字数 vs 官方总字数、评论串数 vs stats 页串数、
字面标签数 + implied 数 vs 侧边栏数。
**它们的价值不在于精确，而在于错了会明显不对。**
